# Середовища NexaFlow

Єдиний перемикач: `appsettings.json`, поле `environment`.

- `develop` (за замовчуванням у Git): локальна база з `api/config.local.php`, пошта в Mailpit на `127.0.0.1:1025`, Telegram вимкнений. Листи переглядайте на http://localhost:8025. Дані живої бази автоматично не підставляються.
- `web`: жива база, PHP mail() хостингу, Telegram увімкнений. Сервер читає секрети з `api/config.web.php`, або зі старого серверного `api/config.local.php`, або `api/config.php` для сумісності.

У `profiles` можна змінити адресу сайту, транспорт пошти і дозвіл Telegram. Паролі й токени не додавайте до JSON. Для окремого локального тестового бота можна ввімкнути `telegram_enabled` у develop і вказати його токен у локальному PHP-конфігу.

## Публікація

Перед першим релізом зробіть резервну копію живої бази й перевірте наявність серверного `api/config.web.php` (або сумісного `config.local.php` / `config.php`). Якщо конфігурації немає, створіть її на сервері з `api/config.example.php`; заповніть пароль БД, адресу/транспорт пошти та Telegram-токен. Не додавайте секрети в Git.

1. Один раз виконайте `database/live_migration.sql` і `database/liqpay_billing.sql` у живій базі (останній створює таблицю підписок, потрібну тарифному API). Для оновлення наявної бази з функцією блокування акаунтів виконайте також `database/account_blocking.sql` один раз. `database/admin_audit.sql` безпечно створює таблицю аудиту й може виконуватись повторно. Для старих назв груп виконайте `database/fix_claim_role_names.sql` один раз. Індекс для очищення історії сповіщень можна безпечно додати через `database/performance_optimization.sql`; скрипт використовує онлайн-операцію InnoDB і його можна запускати повторно. Щоб увімкнути email-сповіщення для наявних користувачів відповідно до налаштування продукту, також один раз виконайте `database/email_notifications_default_on.sql`. Другий файл змінює вимкнені налаштування користувачів на увімкнені, тому не запускайте його повторно після релізу. Стоматологічні API використовують SQL-файли схем із `database/`; cPanel копіює їх у захищену серверну папку, після чого модуль застосовує сумісні `CREATE TABLE IF NOT EXISTS` та доповнення схеми під час першого запиту.

Перед публікацією поточного релізу виконайте `database/accounting_workflow.sql` і `database/accounting_requisites.sql` для нових бухгалтерських таблиць. Перевірте `tasks.due_date`: для старої колонки типу `DATE` після резервної копії виконайте `database/task_due_datetime.sql` у вікно обслуговування. На великій таблиці ця операція може перебудувати таблицю та блокувати записи. Preflight перевіряє наявність `time_entries`, `plan_subscriptions`, основних бухгалтерських таблиць, полів блокування акаунта й тип `tasks.due_date` та зупиняє деплой до копіювання файлів, якщо схема не готова.
2. Виконайте `npm ci`, потім `npm run build:live`. Переконайтеся, що `dist/index.html` та його assets створені, і закомітьте збірку разом із кодом.
3. Запуште коміти. У cPanel Git виконайте Update from Remote, потім Deploy HEAD Commit.
4. `.cpanel.yml` спершу запускає `tools/deployment-preflight.php`: перевіряє production PHP-розширення, серверний конфіг, з’єднання з БД і наявність runtime-схем у релізі. Якщо перевірка не проходить, файли сайту ще не копіюються. Далі деплой копіює `dist` у `public_html/dist`, стоматологічні SQL-схеми у захищену `public_html/database` та переносить кореневий і API `.htaccess`. Це відповідає шляхам у кореневому `.htaccess` і захищає `api/support-private` та SQL-схеми від прямого доступу. Скрипт встановлює `environment: web` лише в опублікованій копії `appsettings.json`; локальний JSON залишається `develop`.
5. Після деплою відкрийте `https://nexaflow.top/`, перевірте вхід, створення задачі й клієнта, email та Telegram (якщо налаштований), завантаження зображення в чаті підтримки. Переконайтеся, що `/robots.txt` і `/sitemap.xml` повертають `200`, а сайт працює через HTTPS.

Сам merge/push не оновлює сайт, якщо автоматичне виконання cPanel deployment не налаштоване. При ручному завантаженні файлів обов’язково встановіть `environment: web` у серверному JSON.

Серверні `config.local.php` і `config.web.php` не перезаписуються деплоєм. Рекомендовано один раз скопіювати наявний серверний конфіг у `api/config.web.php`: усі ключі бази, пошти й Telegram зберігаються. Ці файли ігноруються Git.

Оплата тарифів вимкнена за замовчуванням: вибір тарифу надає його можливості без списання коштів. Платіжна інтеграція збережена, але не активується, доки `billing_enabled` не буде явно встановлено в `true` у серверному `api/config.web.php`. Перед цим необхідно активувати мерчанта та додати бойові `liqpay_public_key` і `liqpay_private_key`. Callback LiqPay використовує `https://nexaflow.top/api/liqpay.php?action=callback`, тому бойовий сайт має бути доступний через HTTPS. Локальні sandbox-перевірки платіжного потоку можна буде ввімкнути окремо, коли це знадобиться.

React звертається до `/api` того самого сайту: готова збірка не містить адреси чужої бази чи API. При `npm run dev` проксі використовує адресу профілю з JSON. Після зміни JSON перезапустіть Vite; PHP та cron читають режим при наступному запуску.

`api/reminders-cron.php` приймає лише CLI-запуски. Додайте його в cPanel Cron Jobs за розкладом, який використовувався на сервері; наприклад, щогодини: `/usr/local/bin/php /home3/nexaflow/public_html/api/reminders-cron.php`. Cron надсилає нагадування і видаляє архів підтримки після 60 днів.

Початковий локальний конфіг (якщо його немає):

```php
<?php
return [
    'host' => '127.0.0.1', 'port' => 3306,
    'database' => 'srm_local', 'username' => 'root',
    'password' => '', 'charset' => 'utf8mb4',
];
```

Вибір середовища не копіює і не очищає базу даних. Налаштування отримання email конкретного користувача продовжують застосовуватися незалежно від середовища.
